## Authentication contract

Web/mobile Firebase SDKs own email/password signup, verification-email delivery, password-reset emails, sign-in and token refresh. Production Firebase configuration must enable Email/Password, allow the intended web domains, configure verification/reset action URLs and provide an appropriate password policy. Signup alone never provisions application database records.

`POST /api/auth/session` receives a Firebase ID token as a Bearer header. Only verified email/password identities can provision an atomic database account/user/workspace/general channel. Repeat calls return the same user. Response is `{ user }`; it does not issue a second authentication token. Firebase UID, not email, is the identity boundary.

`GET /api/auth/me` requires a provisioned verified identity. `POST /api/auth/logout` revokes all-device refresh tokens and clears stored presence. Normal per-device sign-out uses the client Firebase SDK. Every protected request checks Firebase revocation, accepting the remote lookup cost for immediate disabled/revoked identity enforcement.

## Workspace/data contract

All protected calls can set `X-Workspace-Id`. Omission selects the user's oldest membership (workspace ID breaks timestamp ties). Workspace selection does not change the Firebase identity. The membership lookup `GET /api/workspace/:id` authenticates the user independently of this active header, so a saved workspace beyond the first directory page can be validated even when the header refers to a removed workspace. The lookup still requires actual membership and returns 404 for another user's workspace; the exception does not apply to workspace audit reads or tenant resources.

Private-room confidentiality always requires actual channel membership, including workspace owners/admins. Management authority does not bypass this boundary and a read cursor never silently enrolls an administrator. The creator can explicitly invite an administrator from the workspace. Recovery/ownership transfer for an unavailable creator remains a separate future policy. Individual roster entries include `canRemove`; channel DTOs expose `createdById`, `canManageMembers` and `canLeave`.

Directory responses are `{ data, total, hasMore, nextCursor }`, with `currentWorkspaceId` on workspace pages and `canManageMembers` on roster pages. Query schemas are strict: limit defaults to 50 and caps at 100, `after` is an opaque ID of at most 128 characters, and `q` is trimmed and at most 120 characters. Rows sort ascending by the actual membership/channel creation time and then ID; team/roster/candidate cursors are user IDs, workspace cursors are workspace IDs and channel cursors are channel IDs. Cursor validation, rows and the full matching count share one authorized, filtered repeatable-read snapshot. Foreign, inaccessible or no-longer-matching search cursors return 400; clients should reset their page when filters or directory membership change.

Profile freshness does not require downloading every directory page. Clients can derive unique sender IDs from their bounded retained history/pins/action window, request chunks of at most 100 through `/api/team/profiles`, and update their current profile map. The backend applies actual workspace membership to every requested ID and fetches only public fields. Empty batches return an empty array; more than 100 input entries are rejected before deduplication, so repeated IDs cannot bypass the input bound. No historical-message fanout writes occur when a profile changes.

The seventh migration adds ordinary B-tree seek indexes on each scoped timestamp/ID tuple, replacing shorter redundant indexes. It does not require PostgreSQL extension privileges. Case-insensitive substring filtering still needs database work proportional to the searched authorized scope; no trigram extension, constant-time substring search or large-directory latency claim is made. Benchmark with real workload before selecting provider-supported search indexes. Every response remains bounded; clients must use page navigation rather than recursively downloading the entire directory into memory.

History/pin queries accept at most one of `before` or `after`. They return `hasOlder`, `hasNewer`, `olderCursor`, `newerCursor`, plus compatible `hasMore`/`nextCursor` for the queried direction (older for default/`before`, newer for `after`). Navigation flags check existence beyond the returned oldest/newest row in the same repeatable-read snapshot. Cursors are null when there is no page in that direction; on an empty page anchored to a now-unpinned row, the valid anchor ID can still lead back to the remaining pins. Tombstones and unpinned rows are eligible for cursor validation but only live pinned rows are selected for pin content. No global unbounded message count is performed; the existing message `total` remains the selected page length.

Message DTOs include `version`, `updatedAt`, `editedAt`, `deletedAt` and viewer `canEdit`, `canDelete`, `canPin` flags. Deleted messages have an empty body and no code/media/reactions; they retain minimal author/ID/time metadata for stable history. Physical privacy erasure and backup retention need a separate retention policy.

Reaction responses expose only `{ icon, count, reactedByMe }` for the six supported icons. Individual participant rows and IDs are not materialized or exposed by message reads. The aggregation uses only the already-authorized selected message IDs and does not widen workspace/private-room scope. History, pins, change pages and grouped history run their selects/aggregation in bounded PostgreSQL repeatable-read transactions, so versions, counts and cursors come from one snapshot even when another user reacts concurrently. Write responses obtain their summaries before the channel transaction commits, so a subsequent reaction cannot be combined with an earlier message version. PostgreSQL still scans real indexed reaction rows to count them; this bounds application memory and response size rather than claiming constant database cost at any workspace size.

## Durable change ordering and maintenance

Message pages capture their string `changeCursor` before selecting page rows. Every API message create/edit/delete/pin/reaction mutation acquires the same per-channel PostgreSQL advisory transaction lock, updates the message/version and inserts a `MessageChange` record atomically. The next mutation cannot assign/commit a later event until that transaction releases its lock, so readers cannot skip a late-committing earlier event. Event rows carry only message/channel references and sequence/time; responses resolve current server DTOs, never old deleted content.

Clients merge change DTOs by ID/version and advance their cursor only after applying a returned page. Drain `hasMore` pages; an older-history fetch must not reset an established cursor. Pages cap at 100 events and may return fewer distinct messages when one message changed repeatedly. Channels use independent cursors even though the database sequence is global. Invalid or future channel cursors require a history reload rather than silent skipping.

The feed is currently retained durably without automatic pruning or a scheduled maintenance job. Storage grows with actual message mutations. Before long-term scale, define event retention/compaction, an expired-cursor response and snapshot reset protocol, plus tombstone/audit retention and backup erasure policies. No automatic vacuum, unlimited free retention, background pruning or recovery job is claimed. Database/application operators must write through the API or the same ordered transaction protocol to maintain the feed; direct SQL message changes do not automatically create events.

Private membership mutations use the same channel lock as message writes and write audit rows in their transaction. Duplicate member adds are idempotent and do not fabricate extra audit entries. The API exposes no audit edit/delete operation; privileged database operators still control the database, so external tamper-resistant audit storage remains a deployment consideration.

## Database deployment

Use `.env.example` as documentation; supply real secrets through the deployment environment. Firebase Admin uses Application Default Credentials or `FIREBASE_SERVICE_ACCOUNT_JSON`. Never ship service-account credentials to either client. Production rejects Auth emulator configuration and requires an explicit Firebase project and frontend allowlist.

For Neon, configure a TLS PostgreSQL URL, appropriate application connection limit and pool timeout. Run migration deployment against the direct Neon connection using a separate migration role. Run the application with a least-privilege runtime role. The local Compose service is for local PostgreSQL use; it does not create or configure Neon.

New databases: `npm ci`, `npm run prisma:generate`, `npm run prisma:deploy`, `npm run build`, `npm start`. Do not use `prisma migrate dev` or `db push` on production.

Existing databases created with the former `db push` workflow must be backed up and compared against the checked-in baseline before an operator uses `prisma migrate resolve --applied 202610130001_baseline`. Deploy the remaining migrations only after that comparison. The upgrade is transactional: preserved channel rows get separate archived workspaces without memberships, old display/call metadata is archived, message content is preserved, obsolete bcrypt hashes are removed, and old account emails require deliberate administrative Firebase UID linking. Automatic linking by email is intentionally absent. No cleanup script deletes legacy sample data.

The timestamp migration preserves the former Prisma interpretation of naive timestamps as UTC. Before migrating an existing database, verify that historic values actually represent UTC. If the old database generated local-time naive defaults, an operator must reconcile those values before this conversion. Fresh databases store absolute timestamps correctly regardless of database session timezone.

## Container deployment

`Dockerfile` uses Node 24 Debian stages, installs OpenSSL/CA certificates, runs a locked dependency install and Prisma generation/build, prunes development dependencies, and copies only the generated runtime output/dependencies into the final stage. It runs as the unprivileged `node` user. `.dockerignore` excludes environment files, service-account keys, node_modules, tests and build artifacts. Supply secrets at runtime through the orchestrator; no credential build arguments are used.

The runtime uses exec-form `node dist/index.js` so SIGTERM reaches the HTTP drain/shutdown handler. Run migrations separately before rolling out the image. The runtime image is not a migration runner. Deploy behind a TLS-terminating HTTPS proxy; set `FRONTEND_URL` to the deliberate allowlist and `TRUST_PROXY_HOPS` to the actual number of trusted proxy hops. Do not use a blanket trusted-proxy setting. A read-only root filesystem, writable temporary directory and dropped capabilities are appropriate deployment defaults.

`GET /api/health/live` reports the running HTTP process without touching PostgreSQL. `GET /api/health/ready` and the retained `/api/health` report database connectivity and return 503 when disconnected. The Docker healthcheck uses readiness; an orchestrator should use `/live` for liveness to avoid restarting the process merely because PostgreSQL is temporarily unavailable.

## Remaining production blockers/limits

- Real Neon/Firebase credentials, deployed TLS origins, Firebase email action configuration, secret management and backup/restore rehearsal remain operator configuration work. No service was deployed.
- Audio/video calls, screen sharing, recording, stored uploads/voice-note playback, push notifications and real-time delivery do not have infrastructure. Clients must show unavailable states. Media requests fail explicitly rather than storing pretend content.
- Private member administration and message editing/deletion/pinning/profile editing are implemented. Workspace role/member removal, creator ownership transfer/recovery, threads and file access policies still require explicit feature/policy implementation before advertising them.
- In-memory abuse limiting is effective per backend instance: a generous ingress budget of 1,000 requests/minute per IP, a shared protected-route budget of 240 requests/minute per verified database user, and a stricter session/legacy authentication budget of 20 requests per 15 minutes per IP. User keys are derived only after Firebase/database identity verification, never from caller-supplied tokens or headers. An actual middleware test confirms that one limited user cannot consume another user's allowance behind the same IP and that the user's allowance covers multiple routes. Ingress/session limits still need traffic tuning for large shared networks; multiple replicas require a shared limiter store or equivalent edge policy. No distributed limiter is claimed.
- Channel/member/workspace directories and message/pin archives now support bounded complete cursor navigation. Filtered counts/search and unread aggregates still need production workload benchmarks and provider-specific indexing decisions. Polling consumes a real durable bounded message change feed; no WebSocket, push transport or scheduled feed maintenance is claimed.
- Live profile presence represents recent authenticated API activity, not RTC audio/video availability. Firebase token revocation checks add a Firebase lookup on protected requests; capacity/latency should be measured against the deployed project and region.
- Production observability, load testing, database recovery drills and authorization reviews after new features remain required before a production-readiness signoff.
